# P6 Mobile-Lure — Research Plan (W6.5)

> **AUTHORIZATION — LAB ONLY.** All targets are the project's emulators, owned
> devices, and deliberately vulnerable builds (`docs/governance/policy.md` §1).
> Rig-reproduced chains use **historical, already-patched** vulnerabilities
> (policy §7). **Every novel finding routes through policy §7**: coordinated
> disclosure to the vendor, embargo until patch, published output limited to
> class analysis — never a weaponized exploit for an unpatched consumer
> surface.

## 0. Framing and honest expectations

The end-state the research *works toward* is a reverse session from a lab
phone (emulator) to the owner's Kali box, reached via a QR-encoded URL. The
stages below are ordered by what is *guaranteed*:

- **Stage 1 and Stage 2 are engineering**: they produce guaranteed deliverables
  (surface map, patched-class inventory, rig measurements, defender
  telemetry) on a known timeline, because they only use public,
  already-patched vulnerability history.
- **Stage 3 is research**: novel-chain discovery has **no guaranteed
  timeline and no guaranteed yield**. Months of patch-diff archaeology or
  fuzzing may produce nothing exploitable — that is the normal outcome of
  most vulnerability research, and this plan does not promise otherwise.
  The deliverable of Stage 3 is the *methodology plus whatever classes are
  found*, disclosed per §7.

Anything found in Stage 3 is, by construction, a bug in third-party software
on surfaces we do not own as *consumer* surfaces — the disclosure rule is
therefore not a limitation bolted on afterwards, it is the design: the lab
rig is the only place the chain is ever demonstrated.

## 2. Stage 2 — Rig-reproduced historical chains (n-days on vulnerable builds)

**Purpose:** measure the demonstrable QR→shell chain classes on owned rigs
and turn them into defender telemetry. No novel bugs involved.

**Entry criteria:**
- Physical slots completed: Android SDK install, AVD creation,
  rig app build/install (`mobile/rig/README.md` §2).
- Stage-1 artifacts committed.

**Method:**
1. Run the C1 chain per `mobile/rig/harness/run_manifest.json`
   (U→E→C marker sequence + Kali-side session verification).
2. Run the control arm (same URL, stock browser) — must show no
   `BRIDGE_*` markers.
3. Repeat N≥5 runs; record wall-clock per stage (scan/open → bridge reach →
   exec marker → callback received).
4. Optional physical extension: scan the printed sheet with an owned lab
   phone to measure the real scan→open gap (S5), which no adb path can
   reproduce.

**Exit criteria:** one committed run record (markers captured in order,
session proof line from the listener, control arm negative, per-run
timings). Deliverable: `mobile/rig/` measurement summary feeding
`mobile/docs/defender-parity.md` evidence column and, if useful, the P4
detection workstream.

**Stage-2 note on other classes:** C5 (Stagefright-class, page-embedded MP4)
and C6 (Janus-class signature bypass) are candidates for later rig extension
using their public PoCs against matching old API levels — same rules:
historical, patched, owned emulator, benign marker bodies.

## 3. Stage 3 — Novel-chain research (§7-gated)

**Entry criteria:** Stage 2 exit criteria met; this section is the standing
authorization envelope for methodology-only work.

**Targets of interest (all owned or open-source-lab):**
- The rig's own deliberately-vulnerable builds (extend them into new
  deliberately-vulnerable shapes: more bridge methods, scheme-handler
  parsers, file-access combinations).
- Open-source components exercised locally: AOSP WebView/Chromium builds we
  compile ourselves, and the scheme-handler surfaces of scanner apps
  *installed on our own lab devices* — static analysis of APKs we own copies
  of; live probing only against our emulator rigs.
- Patch streams, not products: ASB patch-diff archaeology works on public
  AOSP git history and released bulletin diffs.

**Methodology tracks:**
1. **Patch-diff archaeology.** Monthly ASB diffs (`source.android.com/docs/
   security/bulletin` + AOSP tags) are mined for incomplete or pattern-
   repeated fixes — the classic source of follow-up classes. Output:
   hypotheses tested *only* against our own builds.
2. **WebView/scheme-handler fuzzing hooks.** The rig app is the harness:
   parameterized bridge objects, malformed URL/scheme inputs replayed
   through `load_url.sh` into instrumented builds; crashes land in logcat,
   never near a consumer device. Engine-level fuzzing (V8/JSC) would use
   public fuzzers against locally built engines.
3. **Reachability studies.** Which installed components on a lab image
   still accept legacy-target bridges, implicit intents, or unverified app
   links (the S3/S4 surfaces) — measurement of *our* device image only.

**Every Stage-3 finding: coordinated disclosure per policy §7** —
- Report privately to the vendor's security channel (Google Security Bug
  bounties/issue tracker for Android/Chromium; Apple and WebKit security
  channels for their surfaces) with full repro, on lab-built artifacts.
- Embargo until the vendor patch ships.
- Publish the class analysis in this repo (and papers/), not the turnkey
  exploit, if the surface is consumer-reachable.

**Exit criteria (per finding):** vendor report filed and acknowledged;
embargo respected; class analysis written into the taxonomy/inventory;
defender-parity row added so detection ships at parity (policy §5).
For the track as a whole there is no exit criterion on a deadline — only on
process discipline.

## 4. Physical slots and standing rules

- Human slots that cannot be automated: SDK/Studio install, AVD creation,
  app build, optional physical QR scan with a lab phone.
- No default endpoints anywhere (policy §2); Kali-side listener binds only
  the explicit host/port the operator passes.
- Emulator + owned devices only, forever. Field-adjacent work does not exist
  in P6's scope; if it ever did, it would need the §4 human-subjects path on
  top of §7.
